# Модуль 04: Ембединги та векторний пошук — Лабораторна робота

> **Статус:** Ready for Students — англомовну лабораторну роботу та український переклад затверджено викладачем 2026-10-13

## Мета

Отримати свідчення, потрібні команді інженерів, щоб вирішити, чи має кандидатна конфігурація інформаційного пошуку — пошук на основі ембедингів (`embedding-based retrieval`) — замінити базову конфігурацію експерименту — лексичний пошук (`lexical retrieval`) — для оцінюваного використання операції інформаційного пошуку над канонічною колекцією знань `course-seed-v1`.

## Завдання

- Застосувати дві надані конфігурації розбивки на фрагменти до канонічних записів знань `course-seed-v1` та обрати правило межі, що зберігає значення, потрібне оголошеним випадкам для оцінювання.
- Створити сумісні ембединги одиниць інформаційного пошуку за `representation_contract` у `cases/lab04/stage-c1-fixture.json`, підготувати версійований векторний індекс та спостерегти перевірку прив’язок перед використанням, яка класифікує векторний індекс як застарілий для несумісної потрібної конфігурації інформаційного пошуку.
- Виконати оголошені текстові запити за чотирма порівнюваними конфігураціями інформаційного пошуку та оглянути ранжований кандидатний вихід кожного виконання.
- Зафіксувати одне судження про релевантність для кожної поверненої одиниці інформаційного пошуку й випадку для оцінювання, обчислити `precision@1` і `recall@1` за явними чисельниками та знаменниками й виміряти операційні свідчення.
- Сформулювати одне обмежене рішення щодо конфігурації для оголошених випадків для оцінювання.

## Очікуваний результат

Після завершення лабораторної роботи студент має свідчення, на яких ґрунтується обмежене рішення щодо конфігурації:

- `stage-b/boundary-comparison.json` — обидві надані конфігурації розбивки на фрагменти, застосовані до канонічних записів знань, із фрагментами джерела, які обирає кожна конфігурація;
- `stage-b/boundary-decision.yaml` — зафіксований вибір правила межі, що зберігає значення, потрібне оголошеним випадкам для оцінювання;
- `stage-c1/retrieval-unit-embeddings.json` — один сумісний ембединг одиниці інформаційного пошуку для кожної одиниці інформаційного пошуку обраної конфігурації розбивки на фрагменти;
- `stage-c1/index-manifest.json` — версійований запис векторного індексу: версія канонічної колекції знань, прив’язки представлення, прив’язка розбивки на фрагменти, а також стабільний ідентифікатор пошуку та зв’язок походження кожної проіндексованої одиниці інформаційного пошуку;
- два записи перевірки прив’язок перед використанням — векторний індекс класифіковано як придатний для сумісної потрібної конфігурації інформаційного пошуку та як застарілий для несумісної;
- вісім файлів ранжованого кандидатного виходу в `stage-c2/` — ранжовані одиниці інформаційного пошуку, які повернула кожна з чотирьох порівнюваних конфігурацій інформаційного пошуку для кожного з двох оголошених випадків для оцінювання;
- `stage-c3/relevance-judgments.json` — одне судження про релевантність з обґрунтуванням для кожної поверненої одиниці інформаційного пошуку та випадку для оцінювання;
- `stage-c3/retrieval-metrics.json` — `precision@1` і `recall@1` для кожної конфігурації інформаційного пошуку та випадку для оцінювання, обчислені за явними чисельниками та знаменниками;
- `stage-c3/operational-evidence.json` — виміряна затримка запиту для кожної конфігурації інформаційного пошуку, яка не входить до жодного чисельника чи знаменника метрики;
- `stage-c3/configuration-decision.json` — одне обмежене рішення щодо конфігурації з межею рішення та межею повноважень;
- каталог звітів `reports/lab04/`, який успішно проходить `verify-stage-c3`.

## Очікувані компетентності

Після виконання лабораторної роботи студент уміє:

- Застосовувати конфігурацію розбивки на фрагменти до канонічних записів знань та обирати правило межі, що зберігає значення, потрібне оголошеним випадкам для оцінювання.
- Створювати сумісні ембединги одиниць інформаційного пошуку за контрактом представлення, оголошеним у `cases/lab04/stage-c1-fixture.json`, готувати версійований векторний індекс і незалежно перевіряти прив’язку маніфесту індексу до версії колекції за `required-course-seed-v1` та `required-course-seed-v2` у цій фікстурі, його прив’язки представлення за `representation_contract` у цій фікстурі, прив’язку конфігурації розбивки на фрагменти за `reports/lab04/stage-b/boundary-decision.yaml`, а прив’язки стабільних ідентифікаторів пошуку та зв’язків походження для кожної одиниці — за обраними фрагментами джерела в `reports/lab04/stage-b/boundary-comparison.json`.
- Виконувати чотири конфігурації інформаційного пошуку за оголошеними текстовими запитами та відрізняти ранжований кандидатний вихід від релевантності, від умісту канонічної колекції знань і від подальшої операції з використанням моделі.
- Застосовувати оголошену підставу для судження про релевантність до кожної поверненої одиниці інформаційного пошуку, фіксувати одне судження для кожної поверненої одиниці інформаційного пошуку й випадку для оцінювання та наводити обґрунтування для кожного судження.
- Обчислювати `precision@1` і `recall@1` за явними чисельниками та знаменниками, включно з трактуванням `precision@1` як невизначеного для порожнього ранжованого кандидатного виходу.
- Сформулювати одне обмежене рішення щодо конфігурації з його межею рішення та межею повноважень, а також підтверджувати, що це рішення ані не встановлює якість подальшого визначення поняття, ані не уповноважує зміну канонічної колекції знань.

## Кроки

### Крок студента 1 — Застосувати обидві надані конфігурації розбивки на фрагменти

```bash
uv run learning-project lab04 prepare-boundaries --report-dir reports/lab04
```

Windows PowerShell:

```powershell
uv run learning-project lab04 prepare-boundaries --report-dir reports/lab04
```

Команда застосовує `sentence-pair-v1` і `fixed-72-v1` до канонічних записів знань `R-A` та `R-B` і записує `reports/lab04/stage-b/boundary-comparison.json`. Правило межі `sentence-pair-v1` використовує розмір фрагмента щонайбільше у два речення без перекриття. Правило межі `fixed-72-v1` використовує розмір фрагмента щонайбільше в 72 символи без перекриття. Кожен фрагмент джерела фіксує стабільний ідентифікатор пошуку, текст фрагмента джерела, ідентифікатор і версію канонічного запису знань, ідентифікатор і версію джерела, що його підтверджує, та діапазон символів з індексацією від одиниці.

**Очікуваний результат:** `sentence-pair-v1` створює одиниці інформаційного пошуку `F-A` та `F-B`. `fixed-72-v1` створює від `F-A-72-1` до `F-A-72-4` та від `F-B-72-1` до `F-B-72-2`. Кожен фрагмент джерела фіксує `derived retrieval-side artifact; not a canonical knowledge collection member` як класифікацію належності до колекції.

Команда відмовляється перезаписувати наявний `boundary-comparison.json`. Якщо `boundary-comparison.json` уже існує, зупиніться перед фіксацією іншого рішення про межу та огляньте наявні свідчення Stage B.

### Крок студента 2 — Оглянути контракт інформаційного пошуку, фрагменти джерела та зв’язки походження

```bash
python -m json.tool reports/lab04/stage-b/boundary-comparison.json
```

Windows PowerShell:

```powershell
Get-Content reports/lab04/stage-b/boundary-comparison.json
```

Перевірте, що:

- `retrieval_contract.declared fields` містить текстовий запит, версію канонічної колекції знань, одиницю інформаційного пошуку та правило її межі, конфігурацію інформаційного пошуку, ранжований кандидатний вихід, очікуваний результат, призначений лише для оцінювача, підставу для судження про релевантність, призначеного оцінювача-людину та межу спостереження.
- `canonical_knowledge_collection_version` ідентифікує `course-seed-v1`.
- `canonical_knowledge_records` ідентифікує `R-A` та `R-B` як надані вихідні записи та фіксує `student_generated: false` і `student_approved: false` для обох канонічних записів знань.
- `retrieval configuration roles` призначає `lexical retrieval` базовій конфігурації інформаційного пошуку в експерименті, а `embedding-based retrieval` — кандидатній конфігурації інформаційного пошуку.
- Жоден об’єкт `operation_input` не містить очікуваного результату, призначеного лише для оцінювача.
- Кожен фрагмент джерела містить стабільний ідентифікатор пошуку та зв’язок походження, що містить ідентифікатор канонічного запису знань, версію канонічного запису знань, ідентифікатор джерела, що його підтверджує, версію джерела, що його підтверджує, та точний діапазон символів.

Порівняйте фрагменти джерела, отримані з `R-A`, з підставою для судження про релевантність обох випадків для оцінювання. `F-A` зберігає разом ідентифікатор первинного запису, версію запису й точне місце підтвердного уривка, потрібні за підставою для судження про релевантність. Жоден окремий фрагмент джерела з-поміж `F-A-72-1`–`F-A-72-4` не зберігає всіх трьох потрібних елементів без реконструкції з іншого фрагмента джерела.

### Крок студента 5 — Створити сумісні ембединги одиниць інформаційного пошуку

```bash
uv run learning-project lab04 prepare-embeddings --report-dir reports/lab04
```

Windows PowerShell:

```powershell
uv run learning-project lab04 prepare-embeddings --report-dir reports/lab04
```

Команда зчитує конфігурацію розбивки на фрагменти, зафіксовану в `reports/lab04/stage-b/boundary-decision.yaml`, створює один ембединг одиниці інформаційного пошуку для кожної одиниці інформаційного пошуку, яку включає зафіксована конфігурація розбивки на фрагменти, і записує `reports/lab04/stage-c1/retrieval-unit-embeddings.json`. Кожен зафіксований ембединг одиниці інформаційного пошуку містить стабільний ідентифікатор пошуку та зв’язок походження представленої одиниці інформаційного пошуку, версію представлення, розмірність ембедингу та простір ембедингів.

Команда зупиняється без запису артефакту, якщо обов’язкова локальна модель ембедингу недоступна, і називає команду отримання, яку слід виконати один раз. Команда також зупиняється, якщо:

- завантажена модель не відповідає оголошеному контракту представлення;
- ембединг одиниці інформаційного пошуку має іншу розмірність ембедингу;
- ембединг одиниці інформаційного пошуку містить координату з нескінченним числовим значенням чи значенням, що не є числом.

### Крок студента 6 — Підготувати векторний індекс

### Крок студента 10 — Обчислити та оглянути метрики інформаційного пошуку

```bash
uv run learning-project lab04 compute-retrieval-metrics --report-dir reports/lab04 --model-dir models/potion-base-8M
```

Windows PowerShell:

```powershell

```

Команда повторно перевіряє вісім ранжованих кандидатних виходів перед обчисленням. Змінений вихід Stage C2 зупиняє крок. Команда записує `reports/lab04/stage-c3/retrieval-metrics.json` із записами для окремих випадків та агрегованими записами. Кожен запис містить ранжований кандидатний вихід, оцінені повернені одиниці інформаційного пошуку та обидві метрики з явним чисельником і знаменником. Порожній ранжований кандидатний вихід фіксує `precision@1` як `undefined` із зазначенням причини, а `recall@1` — як `0 of 1`.

**Визначення метрик:**

- `precision@k`: чисельник — це кількість повернених одиниць інформаційного пошуку серед перших `k`, визнаних релевантними; знаменник — це кількість повернених одиниць інформаційного пошуку на цих перших `k` позиціях. `precision@k` є **невизначеним**, а не нулем, якщо ранжований кандидатний вихід не містить жодної одиниці інформаційного пошуку.
- `recall@k`: чисельник — це кількість розглянутих релевантних одиниць інформаційного пошуку, наявних серед перших `k` повернених одиниць інформаційного пошуку; знаменник — це загальна кількість розглянутих релевантних одиниць інформаційного пошуку в очікуваному результаті, призначеному лише для оцінювача. `recall@k` залишається визначеним, коли ранжований кандидатний вихід є порожнім.

**Правило агрегації:** агрегований показник підраховує оцінені повернені одиниці інформаційного пошуку в обох випадках для оцінювання. Порожній ранжований кандидатний вихід не додає жодної оціненої поверненої одиниці інформаційного пошуку до знаменника precision, тоді як розглянута релевантна одиниця інформаційного пошуку в очікуваному результаті, призначеному лише для оцінювача, усе одно входить до знаменника recall.

**Архівовані орієнтовні значення** (виконання з реальною моделлю за оголошеної локальної моделі ембедингу при `k=1`):

| Конфігурація інформаційного пошуку | `precision@1` (агреговане) | `recall@1` (агреговане) |
|---|---|---|
| lexical retrieval | 0 relevant of 1 judged returned = 0.00 | 0 of 2 reviewed relevant = 0.00 |
| embedding-based retrieval | 0 relevant of 2 judged returned = 0.00 | 0 of 2 reviewed relevant = 0.00 |
| hybrid retrieval | 0 relevant of 2 judged returned = 0.00 | 0 of 2 reviewed relevant = 0.00 |
| lexical retrieval followed by embedding-based reranking | 0 relevant of 1 judged returned = 0.00 | 0 of 2 reviewed relevant = 0.00 |

В архівованому виконанні Evaluation Case A створив порожній ранжований кандидатний вихід для лексичної конфігурації та конфігурації з переранжуванням, тому їхній `precision@1` для цього випадку є `undefined`, а не `0.00`. Повідомте значення з вашого власного запуску; вони залежать від ранжованих кандидатних виходів і зафіксованих вами суджень про релевантність.
